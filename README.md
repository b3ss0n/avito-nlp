# Кандидатогенерация для категории «Услуги» Авито

Тестовое задание: для поискового запроса отобрать из корпуса 189 212 объявлений
до 50 кандидатов для дальнейшего ранжирования. Метрика — Recall@50.

## Итоговый подход

Двухэтапная схема:

1. **Пул кандидатов (~300 на запрос)** — лексический поиск BM25:
   * три отдельных индекса: заголовок, параметры (`item_infm_params_text`), описание;
   * выдачи полей объединяются Reciprocal Rank Fusion;
   * три выдачи, объединённые без повторов:
     **локальная** (объявления из локации запроса, топ-300),
     **соседняя** (объявления в радиусе 100 км, кроме самой локации, топ-100),
     **глобальная** (весь корпус, топ-100).
2. **Ранкер CatBoost** (бинарная классификация «выбран / не выбран») выбирает из
   пула 50 объявлений. Признаки:
   * скоры BM25 по полям, места в локальной / соседней / глобальной выдаче;
   * расстояние от центра локации запроса до объявления;
   * доля слов запроса в заголовке, длины текстов, число клонов объявления;
   * **соответствие подкатегории запросу**: по train считаем P(подкатегория | слово
     запроса), для кандидата берём вероятность его подкатегории (см. ниже);
   * **смысловая близость**: косинус эмбеддингов запроса и заголовка
     (`multilingual-e5-small`) — ловит перефразировки, которые BM25 не видит;
   * рейтинг, число отзывов, цена, флаги контактов.

## Результаты

| Шаг | Recall@50 val | Recall@50 LB |
|---|---|---|
| BM25 по 3 полям + RRF | 0.415 | 0.328 |
| + локальная выдача по локации запроса | 0.764 | 0.730 |
| + ранкер CatBoost поверх пула (локальная + глобальная выдачи) | 0.802 | 0.769 |
| + соседние локации в пуле | 0.816 | — |
| + признак соответствия подкатегории | 0.828 | **0.786** |
| + признак косинуса эмбеддингов e5 | 0.830 | — |

Эмбеддинги дали +0.2 п.п. — в пределах шума: признак модель использует
(важность ~6%), но при ранкере, уже берущем ~95% потолка пула, новой
информации сверх BM25 и подкатегории в нём немного.

Потолок пула (Recall идеального ранкера) — 0.874: ранкер реализует ~95% от
возможного. Валидация стабильно предсказывает лидерборд с разрывом 3–4 п.п.
(подробнее — в разделе про валидацию).

## Ключевые наблюдения из данных

* **Локация — главный сигнал.** 75–83% выбранных объявлений находятся в той же
  локации, что и запрос. В локации запроса обычно ~1000 объявлений вместо 190k,
  поэтому поиск внутри локации резко упрощает задачу.
* **Клоны.** У 52% объявлений корпуса полностью совпадает заголовок с другими —
  один исполнитель публикует одно объявление в разных городах. У клонов
  одинаковый BM25, и без учёта локации правильная копия теряется среди
  остальных (Recall для ответов с >50 клонами — 0.24 против 0.44 без клонов).
  Именно это объясняло начальный разрыв валидации и лидерборда.
* **Прямое запоминание не работает.** Только ~8% правильных ответов валидации
  лежат в `benchmark_items`, поэтому «вернуть то, что выбирали по этому запросу
  раньше» почти ничего не даёт — нужен поиск по тексту. Train полезен косвенно:
  через статистику «слово запроса → подкатегория» и как обучающая выборка ранкера.

## Почему соседние локации, а не эмбеддинги

Перед добавлением нового источника кандидатов разобрал, почему правильные
ответы валидации не попадают в пул (пул без соседней выдачи, потолок 0.853;
`uv run python -m src.analysis misses` — на текущем пуле покажет, что осталось):

| Причина промаха | Доля ответов |
|---|---|
| есть общие слова с запросом, но объявление в **другой локации** | 9.2% |
| нет общих слов, та же локация | 4.0% |
| нет общих слов, другая локация | 0.8% |
| есть общие слова, та же локация, но за пределами топ-300 | 0.6% |

Главная дыра — соседние локации (область, города-спутники): лексически
объявление находится, но глобальный топ-100 забит клонами со всей страны.
Промахов «нет общих слов», где помогли бы эмбеддинги, меньше 5%, и по
примерам это чаще шум, чем перефразировки («lpg массаж» → «перманентный
макияж»). Поэтому добавлена выдача по радиусу 100 км (медиана расстояния до
«чужих» правильных ответов — 39 км): потолок пула вырос 0.853 → 0.874, доля
промахов «общие слова есть, другая локация» снизилась 9.2% → 7.2%.

## Признак подкатегории и утечка таргета

`P(подкатегория | запрос)` — среднее по словам запроса частот
`P(подкатегория | слово)`, посчитанных по train (по сути target encoding слов).
Как и target encoding, его нельзя считать на тех же строках, на которых учится
модель: иначе признак содержит правильный ответ запроса. Поэтому статистика
считается по `train_stats` — train без сессий обучающих запросов ранкера и без
валидации. Вклад признака на валидации: +1.2 п.п. (0.816 → 0.828).

## Валидация

Устроена так же, как бенчмарк (`src/validation.py`):

* **запрос = поисковая сессия**: строки train с одинаковыми текстом, локацией,
  фильтрами, флагом доставки и категорией; выбранные в ней объявления — правильные ответы;
* в бенчмарке все тексты уникальны, поэтому берём **один случайный текст → одну его
  сессию**. При такой схеме доля текстов, встречающихся в оставшемся train,
  получается 38.8% (в бенчмарке 37%) — без ручной подгонки;
* **групповое разбиение**: сессия целиком уходит либо в обучение, либо в валидацию;
* **псевдо-корпус**: объявления бенчмарка + правильные ответы валидации
  (иначе правильных ответов просто нет в корпусе).

Обучающие запросы для ранкера (6000) набираются из оставшегося train тем же
способом и с валидацией не пересекаются. Для финального ответа ранкер
переобучается на обучающих + валидационных запросах: все решения о признаках
и параметрах принимались на валидации до этого.

Разрыв валидация → лидерборд: сначала был 8.5 п.п. (BM25 без локации). Разбор
показал причину — клоны (в валидации у 60% правильных ответов их нет, в
бенчмарке, судя по корпусу, больше). После учёта локации разрыв сократился до
3–4 п.п., и порядок методов на валидации совпадает с лидербордом. Ещё одно
известное отличие: у 9% запросов бенчмарка `search_category = 0`, в train таких
сессий нет.

## Ограничения и что можно сделать дальше

* **Эмбеддинги как источник кандидатов** (dense-поиск внутри локации) — закроют
  часть промахов «нет общих слов» (~5%). Сейчас эмбеддинги используются только
  как признак ранкера: разбор промахов показал, что соседние локации дают больше
  за меньшую цену, а кодирование всего корпуса на CPU дорогое.
* **Нормализация «двойников»**: в описаниях встречаются латинские буквы вместо
  кириллицы («Bеcь пpoцесc»), такие слова сейчас рвутся на мусорные токены.
* **Ранкер**: `YetiRank` вместо бинарной классификации, подбор числа итераций
  (лосс ещё снижался на 500 итерациях), проверка значимости приростов
  парным бутстрепом.
* **Запросы с `search_category = 0`** (9% бенчмарка) — отдельная обработка.

## Как воспроизвести

```bash
uv sync                               # окружение (Python 3.12)
# положить train.parquet, benchmark_items.parquet, benchmark_queries.parquet в dataset/
uv run python -m src.prepare          # нормализация текстов -> cache/ (~7 мин)
uv run python -m src.validation       # валидационное разбиение
uv run python scripts/download_model.py  # один раз скачать e5 в models/ (дальше всё офлайн)
uv run python -m src.ranker pools     # пулы кандидатов, только подготовка данных (~25 мин)
uv run python -m src.embeddings       # эмбеддинги запросов и объявлений из пулов (~20 мин на CPU)
uv run python -m src.ranker val       # обучение на запросах ранкера, Recall@50 на валидации (~6 мин)
uv run python -m src.ranker submit    # обучение на всех размеченных запросах, answer.csv (~8 мин)
uv run python -m src.bm25 val         # (опционально) бейзлайн BM25 + локация без ранкера
```

## Структура

| Файл | Что делает |
|---|---|
| `src/text.py` | нормализация текста: lowercase, токенизация, стемминг, стоп-слова |
| `src/prepare.py` | нормализует все тексты один раз и кэширует |
| `src/validation.py` | валидационное разбиение, псевдо-корпус, Recall@k |
| `src/bm25.py` | BM25 по трём полям + RRF + локальная выдача (бейзлайн без ранкера) |
| `src/candidates.py` | пул кандидатов и признаки для ранкера |
| `src/embeddings.py` | эмбеддинги e5 и признак косинусной близости |
| `src/ranker.py` | обучение CatBoost и сборка ответа |
| `src/analysis.py` | анализ, на котором основаны решения: разрыв val/LB, локация, клоны, промахи пула |
| `scripts/download_model.py` | однократная загрузка весов e5 |

## Использованные библиотеки

* [bm25s](https://github.com/xhluca/bm25s) — BM25;
* [snowballstemmer](https://github.com/snowballstem/snowball) — стемминг русского и английского;
* [CatBoost](https://catboost.ai/) — ранкер;
* [sentence-transformers](https://www.sbert.net/) + модель
  [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)
  (MIT) — эмбеддинги; веса скачиваются один раз, инференс локальный на CPU;
* pandas, numpy, pyarrow, scikit-learn.

Внешние API не используются, всё считается локально на CPU.
