# Кандидатогенерация для категории «Услуги» Авито

Тестовое задание: для поискового запроса отобрать из корпуса 189 212 объявлений
до 50 кандидатов для дальнейшего ранжирования. Метрика — Recall@50.

## Итоговый подход

Двухэтапная схема:

1. **Пул кандидатов (~225 на запрос)** — лексический поиск BM25:
   * три отдельных индекса: заголовок, параметры (`item_infm_params_text`), описание;
   * выдачи полей объединяются Reciprocal Rank Fusion;
   * две выдачи: **локальная** (только объявления из локации запроса, топ-300)
     и **глобальная** (весь корпус, топ-100).
2. **Ранкер CatBoost** выбирает из пула 50 объявлений. Признаки: скоры BM25 по
   полям, места в локальной/глобальной выдаче, расстояние от центра локации
   запроса до объявления, доля слов запроса в заголовке, число клонов
   объявления, рейтинг, цена и т.п.

## Результаты

| Шаг | Recall@50 val | Recall@50 LB |
|---|---|---|
| BM25 по 3 полям + RRF | 0.415 | 0.328 |
| + локальная выдача по локации запроса | 0.764 | 0.730 |
| + ранкер CatBoost поверх пула | 0.802 | — |

## Ключевые наблюдения из данных

* **Локация — главный сигнал.** 75–83% выбранных объявлений находятся в той же
  локации, что и запрос. В локации запроса обычно ~1000 объявлений вместо 190k,
  поэтому поиск внутри локации резко упрощает задачу.
* **Клоны.** У 52% объявлений корпуса полностью совпадает заголовок с другими —
  один исполнитель публикует одно объявление в разных городах. У клонов
  одинаковый BM25, и без учёта локации правильная копия теряется среди
  остальных (Recall для ответов с >50 клонами — 0.24 против 0.44 без клонов).
  Именно это объясняло начальный разрыв валидации и лидерборда.
* **Прямое запоминание не работает.** Только ~8% правильных ответов валидации
  лежат в `benchmark_items`, поэтому «вернуть то, что выбирали по этому запросу
  раньше» почти ничего не даёт — нужен поиск по тексту.

## Валидация

Устроена так же, как бенчмарк (`src/validation.py`):

* **запрос = поисковая сессия**: строки train с одинаковыми текстом, локацией,
  фильтрами, флагом доставки и категорией; выбранные в ней объявления — правильные ответы;
* в бенчмарке все тексты уникальны, поэтому берём **один случайный текст → одну его
  сессию**. При такой схеме доля текстов, встречающихся в оставшемся train,
  получается 38.8% (в бенчмарке 37%) — без ручной подгонки;
* **групповое разбиение**: сессия целиком уходит либо в обучение, либо в валидацию;
* **псевдо-корпус**: объявления бенчмарка + правильные ответы валидации
  (иначе правильных ответов просто нет в корпусе).

Обучающие запросы для ранкера набираются из оставшегося train тем же способом
и с валидацией не пересекаются.

## Как воспроизвести

```bash
uv sync                               # окружение (Python 3.12)
# положить train.parquet, benchmark_items.parquet, benchmark_queries.parquet в dataset/
uv run python -m src.prepare          # нормализация текстов -> cache/ (~7 мин)
uv run python -m src.validation       # валидационное разбиение
uv run python -m src.ranker pools     # пулы кандидатов (~20 мин)
uv run python -m src.ranker val       # Recall@50 на валидации
uv run python -m src.ranker submit    # answer.csv
```

## Структура

| Файл | Что делает |
|---|---|
| `src/text.py` | нормализация текста: lowercase, токенизация, стемминг, стоп-слова |
| `src/prepare.py` | нормализует все тексты один раз и кэширует |
| `src/validation.py` | валидационное разбиение, псевдо-корпус, Recall@k |
| `src/bm25.py` | BM25 по трём полям + RRF + локальная выдача (бейзлайн без ранкера) |
| `src/candidates.py` | пул кандидатов и признаки для ранкера |
| `src/ranker.py` | обучение CatBoost и сборка ответа |

## Использованные библиотеки

* [bm25s](https://github.com/xhluca/bm25s) — BM25;
* [snowballstemmer](https://github.com/snowballstem/snowball) — стемминг русского и английского;
* [CatBoost](https://catboost.ai/) — ранкер;
* pandas, numpy, pyarrow, scikit-learn.

Внешние API не используются, всё считается локально на CPU.
